Run destructive/failure tests locally or against isolated staging only. Do not cause repeated real Gmail/Kindle sends.

Required evidence:

2. Assistant Queue enqueue failure rolls back both assistant job and Telegram update claim; retry succeeds.
3. Duplicate/replayed book Queue messages do not execute concurrently while an active task_execution_leases row exists.
4. Expired book lease can be reclaimed after simulated hard crash.
5. HTTP POST /api/v1/tasks with the same Idempotency-Key returns the same logical task rather than creating two tasks.
6. Injected HTTP Queue enqueue failure returns 503 and leaves no orphan task/key reservation.
7. Irrelevant source candidates are rejected before ranking.
8. Invalid EPUB/PDF signature, oversized download, source failure, R2 PUT failure and missing staged object do not reach Gmail send.
9. Gmail fence: accepted receipt replay performs no second Gmail send.
10. Gmail fence: uncertain/network-lost send becomes unknown and automatic resend is blocked.
11. Simulated crash after Gmail acceptance but before TaskRecord update recovers the persisted accepted receipt rather than resending.
12. Telegram final sendMessage failure leaves the assistant job retryable/diagnosable and does not duplicate its logical task.

Automated tests may supply evidence for cases already covered, but staging-specific state/Queue behavior should be demonstrated where practical.
